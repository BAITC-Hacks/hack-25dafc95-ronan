# План реализации EKT Assistant

**Статус:** проектный план, не отчёт о готовой системе. На момент уточнения задания до сдачи было около трёх часов; этапы задают приоритеты, а не обещание конкретного времени исполнения.

## 1. Результат, который показываем жюри

Один законченный путь: запрос товара → карточка с источником данных и остатком по выбранному складу → предложение с количеством и ценой → явное подтверждение → изменение корзины → открытие той же корзины по ссылке. Отдельные проверки: нулевой остаток и объяснимый аналог, условия покупки, отсутствие сертификата, конфликт характеристик.

Не начинать с копии всего интернет-магазина. Достаточно страницы демонстрации, встроенного чата, карточек и рабочей страницы демо-корзины. Скриншоты сайта — ориентир оформления, а не доказательство устройства его backend.

## 2. Выбор модели для работы в Codex

По официальным материалам, проверенным 23.09.2026, доступны разные поколения и уровни; конкретный список зависит от аккаунта и клиента [W1–W3, SOURCES.md].

Предлагаемый рабочий выбор: GPT-6 Sol с Medium, когда он доступен. Для сложной архитектуры и финального ревью — Astra с Light/Medium. Для небольших однозначных задач — Luna. Из пары GPT-5.6 Luna / Terra для основной интеграции предпочесть Terra, а Luna оставить на узкие задания с тестами. Это рекомендация для этой задачи, не результат сравнительного теста вашего репозитория. Не включать Max/Ultra для каждого изменения.

Модель внутри будущего консультанта выбирается отдельно: конфигурация `OPENAI_MODEL`, проверки на ваших запросах, ограничения стоимости и времени. Выбор в интерфейсе Codex не подключает модель к серверному приложению.

## 3. Распределение команды

| Участник | Зона ответственности | Первый результат |
|---|---|---|
| Ты: backend | API, каталог, PostgreSQL, сессии, правила корзины, интеграции и серверные тесты | Документированный контракт и API карточки товара |
| Второй: frontend | Виджет чата, карточки, подтверждение, загрузка файлов, страница `/cart`, адаптивность | Интерфейс на согласованных mock-ответах |
| Третий: AI / данные / QA | Интерпретация запросов, промпты, проверенные правила аналогов и условия магазина, набор тестов, демо | Контракт LLMProvider, тестовые сценарии и список недостающих данных |

Третий участник не меняет корзину напрямую. Backend владеет бизнес-инвариантами, общие схемы согласуются в `packages/contracts`. Назначить владельцев модулей, чтобы агенты не переписывали одни файлы одновременно.

## 4. Что уточнить у партнёра сразу

Главный блокер — корзина: тестовый API записи, связывание корзины с текущим посетителем сайта, допустимый метод интеграции, ссылка на корзину, идемпотентность, проверка доступности на стороне магазина. Узнать, примут ли на промежуточном демо отдельную корзину с явным обозначением.

Следующий блок — данные: ссылки или поля сертификатов; утверждённые условия оплаты, доставки и минимальной партии; валюта и трактовка цены; единицы, шаг и минимум количества; какие склады доступны для продажи и как выбирается регион. Уточнить семантику `KRATNOST_MIN`, `RECOMMEND`, `offers` и расхождения 160 А / 250 А.

Наконец — ограничения API: лимиты, допустимая частота обновления, полный объём каталога, окончание пагинации, наличие поиска и фильтров. Не придумывать недокументированные query-параметры.

## 5. Архитектура MVP

Один backend на TypeScript, Fastify и PostgreSQL. TypeScript strict, Zod для схем и проверок, Vitest для тестов, Docker Compose для окружения. В свежем проекте — Node.js 24 LTS [W6]. Схемы запросов и ответов согласовать с механизмом валидации Fastify [W7]. Конкретные совместимые версии зафиксировать при установке.

```text
apps/web              — чат и страница корзины; другой участник
apps/api/src
  modules/catalog     — импорт, поиск, карточки, свойства
  modules/cart        — предложения, подтверждения, корзина
  modules/chat        — история сессии, маршрутизация, инструменты
  modules/policies    — утверждённые условия магазина
  modules/attachments — безопасное извлечение и сопоставление
  providers/ekt       — только документированные вызовы EKT
  providers/llm       — stub / OpenAI
  providers/cart      — demo / EKT adapter с явным блокером
  plugins             — БД, сессии, CSRF, ошибки, логирование
packages/contracts    — общие схемы/API
samples               — исходные снимки и отдельно synthetic fixtures
```

Не нужны обучение модели, Kubernetes, Kafka, самостоятельная векторная БД или многoагентная система в runtime. Для начала достаточно точных индексов, фильтров по нормализованным свойствам и текстового поиска. `pg_trgm` можно добавить для нечёткого совпадения названий [W8]. Он не заменяет проверку технической совместимости.

## 6. Этапы и критерии выхода

### Этап 1. Контракт, каркас и каталог

Проверить репозиторий; настроить workspace backend, конфигурацию, миграции, обработку ошибок, health endpoint и OpenAPI. Создать FixtureCatalogProvider и EktCatalogProvider с подставляемым HTTP-клиентом. Live-проверки запускаются отдельно и не требуются для прохождения offline unit-тестов.

Импортировать страницу 2 из samples и карточку 515291. Не заполнять отсутствующие карточки или остатки догадками. Сохранять raw JSON и нормализованную проекцию с источником каждого важного поля. Реализовать поиск по внутреннему ID, артикулу, коду поставщика и названию.

**Выход:** приложение стартует локально; `/api/health`, поиск и карточка работают на снимках; конфликт 160/250 отображается; отсутствие detail не выдаётся за отсутствие товара; тесты и README соответствуют реальности. Для сегодняшнего демо сразу продолжить минимальными частями этапов 2–3 до рабочего вертикального сценария.

### Этап 2. Сессия и безопасная демо-корзина без LLM

Создать анонимную сессию с HttpOnly cookie и CSRF-защитой. Реализовать предложение изменения и отдельное подтверждение. Обеспечить владение ресурсами, срок действия, версии, транзакцию, повторную проверку, идемпотентность и подсчёт существующего количества.

Добавить отдельно помеченные synthetic fixtures с документированными demo purchase rules. Они нужны для полностью управляемых тестов корзины: исходных данных недостаточно для подтверждения всех реальных правил продажи.

**Выход:** интеграционные тесты показывают, что без подтверждения корзина неизменна, повторы не дублируют позиции и чужая сессия не может получить доступ. Frontend открывает `/cart` с актуальным состоянием; это не endpoint магазина EKT.

### Этап 3. Чат и LLM-инструменты

Подключить LLMProvider. Начать со stub для воспроизводимых тестов, затем добавить реальный API-провайдер. Разрешить только предметные инструменты с валидируемыми аргументами. Вызов функции со строгой схемой помогает контролировать форму, но не доказывает истинность фактов [W5].

Критические значения карточек, итогов, остатков и ссылок формирует сервер. LLM извлекает запрос и помогает объяснить уже проверенные результаты. Подтверждение обрабатывается сервером отдельно; инструмента `confirm_cart` у модели нет.

**Выход:** один свободный запрос проходит всю цепочку до предложения; действие пользователя подтверждает его; система использует историю только своей сессии и корректно отвечает при сбое модели.

### Этап 4. Аналоги, условия покупки и сертификаты

Подготовить репрезентативную выборку нескольких товарных групп; первоначальная алфавитная страница не доказывает покрытие всего каталога. Для аналогов — тип товара, проверенные существенные параметры, наличие, объяснение совпадений и отличий. Для электротехнических замен правила должны быть подтверждены специалистом; сходство названия не гарантирует заменяемость.

Если критические поля отсутствуют или конфликтуют, сообщать об ограничении и передавать вопрос менеджеру, а не объявлять товар совместимым. Для обязательного демо нулевого остатка использовать проверенную пару либо явно синтетическую пару с полным набором demo-правил. Не выбирать аналог по `RECOMMEND` без подтверждения значения этого поля.

Условия покупки хранить как версии утверждённых материалов с происхождением. Отдельный synthetic-набор допустим только в demo-режиме. Сертификат показывать исключительно при реально имеющейся ссылке/файле. Отсутствие поля означает «в доступных данных не найден», а не «сертификата не существует».

**Выход:** все пять обязательных сценариев имеют тест и воспроизводимое демо; реальные и synthetic источники не смешаны.

### Этап 5. Вложения

Поддержать современные Excel/Word (`.xlsx`, `.docx`) и PDF с текстовым слоем; затем фото JPEG и сканы через отдельный включаемый vision-провайдер. Поддержку старых `.xls`/`.doc` и прочих форматов явно зафиксировать как реализованную либо отсутствующую; не обещать её по одному общему слову «Word».

Результат: таблица извлечённых позиций с исходной строкой, номером листа/страницы, количеством, кандидатом и статусом сопоставления. Пользователь проверяет её до формирования предложения корзины. Никакого добавления только из-за текста внутри вложения.

Ограничить размер, страницы, строки, размер распаковки и время; не исполнять макросы, формулы, вложенные объекты и внешние ссылки. Файлы приватны, привязаны к сессии и автоматически удаляются. Отправка во внешний AI — только явно разрешённый путь; не отправлять платёжные реквизиты.

**Выход:** поддерживаемые типы проходят проверку; неподдерживаемые получают явную ошибку; в README перечислены реальные возможности и пределы.

### Этап 6. Интеграция, проверка и защита

Собрать frontend и backend; проверить session-cookie через dev proxy и на итоговом домене. Измерить отдельно время получения фактов, время первого ответа и полного ответа; не выдавать имитацию печати за соблюдение «единиц секунд».

Проверить реальные доступы, если они выданы; внешний EKT cart adapter включать только с документированным контрактом. При неизвестном исходе записи после таймаута не повторять её вслепую.

Подготовить видео/сценарий демо и README с проверенными командами, источниками и известными ограничениями. Все неподключённые интеграции обозначить честно. Кодексу дать отдельное ревью на отсутствие обходов подтверждения и утечек секретов.

## 7. Стратегия поиска и обновления

Первый приоритет — точное совпадение артикула/ID/кода поставщика. Затем фильтры по типу и параметрам, текстовое ранжирование и нечёткий поиск. Совпадение по названию используется для кандидатов, не для доказательства совместимости.

Синхронизация — отдельная ограниченная команда, не полный обход API на каждый запрос и не неограниченный процесс при старте сервера. Для постраничного чтения нужны дедупликация по ID, проверка повторяющихся страниц, лимит запросов и явный статус частичного импорта. Поле `count=20` не трактуется как размер всего каталога.

Свежие карточки выбранных товаров запрашиваются по потребности. Короткий кэш допускается для консультации с указанием времени; подтверждение корзины использует повторную проверку, а не вчерашний индекс. Ошибка источника не равна нулевому остатку.

## 8. Демо и критерии продукта

Показать сначала полезную консультацию, затем отсутствие самовольной записи, подтверждённую запись и открытие корзины. После — аналог при нулевом остатке и обнаруженное расхождение каталога. На экране всё время видны режим корзины и происхождение данных.

Для будущего продукта измерять: время до подходящего товара, долю подтверждённых добавлений, передачу менеджеру, долю ответов с проверяемым основанием и число ошибочных товарных утверждений. Рост конверсии пока гипотеза: результатов продаж в предоставленных данных нет.
